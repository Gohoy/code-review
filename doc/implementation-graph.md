# 统一图的代码实现层定义

## 1. 目标

代码实现层描述指定 Git commit 上“当前代码实际是什么”，为统一图中的 `AS_IS` 需求与技术设计提供证据。它不是 AI 对架构好坏的评价，也不能用计划节点假装代码已经存在。

同一 commit、同一扫描器版本和同一配置必须生成相同的确定性节点与关系。AI 只能补充明确标记为 `INFERRED` 的关系，不能覆盖扫描事实。所有节点与关系直接加入[统一交互图](graph-model.md)，不维护第二份“技术图”。

## 2. 跨层追踪

```text
需求层
    └── realized_by
        技术设计层
            └── implemented_by
                代码实现层
                    └── verified_by / evidenced_by
                        测试证据层
```

- 页面默认只投影候选用户主线；用户展开层级后，在同一画布显示关联设计、代码和测试节点。
- 未被任何需求或设计关联的代码节点仍需保留，并显示为“尚未解释”。
- 一个用户行为可以跨多个仓库；一个技术节点也可以支持多个用户行为。

## 3. 代码实现与测试节点

| 类型 | 含义 | 稳定标识依据 |
| --- | --- | --- |
| `Repository` | 一个 Git 仓库快照 | 仓库标识 + commit |
| `Module` | Python 模块或 TypeScript 模块 | 仓库 + 规范化文件路径 |
| `Symbol` | 类、函数、方法或组件 | 仓库 + 文件路径 + 完整符号名 |
| `EntryPoint` | 页面、HTTP 路由、事件、定时任务或 CLI | 协议类型 + 规范化入口标识 |
| `DataEntity` | 实际数据库表或稳定持久化实体 | 存储类型 + 规范化实体名 |
| `ExternalSystem` | 从代码确认的 GitLab、Hi、Claude、COS 等进程外依赖 | 稳定系统名称 |
| `Test` | 测试证据层中的自动测试或可执行验收场景 | 仓库 + 文件路径 + 测试完整名称 |
| `Configuration` | 会改变行为的部署或运行配置 | 配置作用域 + 固定配置名 |

局部变量、表达式和普通字段第一版不建节点，避免图被语法细节淹没。文件可以作为 `Module` 节点在用户展开实现层后显示，不会出现在默认需求投影。

## 4. 实现与证据关系

| 关系 | 含义 |
| --- | --- |
| `contains` | 仓库、模块或符号包含下一级元素 |
| `imports` | 模块直接导入另一个模块或符号 |
| `calls` | 一个入口或符号调用另一个符号 |
| `exposes` | 入口暴露某个符号提供的行为 |
| `reads` | 符号读取数据实体 |
| `writes` | 符号写入数据实体 |
| `invokes` | 符号调用外部系统 |
| `verifies` | 测试直接覆盖入口、符号或用户场景 |
| `configured_by` | 行为受到某项配置控制 |
| `implemented_by` | 技术设计或需求由代码节点实现 |
| `evidenced_by` | 节点或关系由具体源码或运行记录证明 |

静态分析无法可靠确认动态分派时，关系必须标记为 `INFERRED` 或保留为断裂引用，不能伪装成确定调用。设计层的计划接口和数据实体不得被直接复用为代码事实；扫描到实际实现后创建实现层节点，再用 `implemented_by` 连接。

## 5. 源码证据

每个技术节点和关系至少保存：

- 仓库标识和 commit SHA。
- 文件规范化路径。
- 完整符号名；文件级事实可以为空。
- 起止行或语法节点范围。
- 提取器名称和版本。
- 来源：`DERIVED`、`OBSERVED` 或 `INFERRED`。
- 原始证据摘要；不得保存凭证或环境变量值。

稳定 ID 不包含行号或 commit，因此代码移动和 revision 对比不会把同一符号误判为全新业务需求。无法确定重命名时按删除与新增展示，不由 AI 静默合并。

## 6. 扫描结果必须展示的缺口

- 未支持语言和无法解析的文件。
- 无法解析目标的 import、调用、数据读写和外部调用。
- 没有关联用户行为的入口与符号。
- 没有关联实现证据的候选用户行为。
- 没有关联测试的入口、写操作和叶子场景。
- AI 推断产生的节点和关系。
- 仓库 HEAD 已经不同于模型 commit 的过期状态。

这些是结果的一部分。任一缺口都不得被“扫描完成”状态隐藏，也不得自动删除代码图中无法解释的节点。

## 7. 扫描与更新

1. 校验输入是允许读取的本地工作区，发现其中的 Git 仓库并等待用户确认扫描范围。
2. 分别记录各仓库身份、commit 和脏工作区状态；第一版只扫描已提交内容。
3. 读取项目清单和语言信息。
4. 运行确定性语言与框架提取器。
5. 合并、校验并把候选实现节点与关系加入新的完整图 revision。
6. AI 读取实现层和必要源码，聚合候选需求层并关联既有设计层。
7. 校验每个 AI 结论都关联技术证据，否则标记 `UNRESOLVED`。
8. 生成候选统一图 `AS_IS` revision 并在同一画布展示。
9. 仓库 commit 变化后重新扫描，生成节点、关系、属性和缺口 Diff。

扫描器失败必须保留上一个成功 revision，并显示本次失败原因；不得发布半份新图覆盖旧图。

## 8. 第一里程碑验收场景

### `SCN-ASIS-IMPORT-001` 接入本地工作区

- Given：用户提供一个允许读取、包含一个或多个 Git 仓库的本地工作区路径。
- When：用户要求建立当前代码模型。
- Then：系统展示发现的仓库，用户确认范围后分别记录 commit 并开始只读扫描，不修改目标仓库。

### `SCN-ASIS-GRAPH-001` 生成确定性技术图

- Given：仓库包含第一版支持的代码。
- When：扫描完成。
- Then：入口、符号、表和外部系统形成代码实现层，测试形成测试证据层；相同输入重复扫描结果一致。

### `SCN-ASIS-GAP-001` 展示扫描缺口

- Given：仓库包含不支持的文件或无法解析的动态关系。
- When：扫描完成。
- Then：系统保留已确认事实，并明确显示所有未解析项；不得猜测为确定事实。

### `SCN-ASIS-BEHAVIOR-001` 聚合候选用户主线

- Given：技术图已经冻结。
- When：AI 分析当前代码行为。
- Then：系统生成自然语言用户主线，每个节点关联技术证据；AI 推断明确标记为 `INFERRED`。

### `SCN-ASIS-EXPLORE-001` 从行为下钻到代码

- Given：候选统一图已经展示。
- When：用户点击行为节点。
- Then：系统在同一画布展开相关入口、调用链、方法、表、外部调用和测试节点，并在节点详情显示可定位源码证据。

### `SCN-ASIS-STALE-001` 识别模型过期

- Given：模型记录的 commit 与仓库当前 HEAD 不同。
- When：用户再次打开项目。
- Then：系统把模型标记为过期，仍允许查看旧模型，但不把它描述为当前代码。

### `SCN-ASIS-RESCAN-001` 展示代码模型差异

- Given：仓库产生新的已提交 commit。
- When：用户重新扫描。
- Then：系统创建新的候选 revision，展示行为、技术证据和扫描缺口的语义 Diff，旧 revision 保持不变。

### `SCN-ASIS-APPROVE-001` 批准当前代码基线

- Given：候选用户主线不存在 `UNRESOLVED`。
- When：用户明确批准。
- Then：系统冻结不可变 `AS_IS` revision；后续新需求只能基于该 revision 设计。
