# sdbp-review 需求基线

## 目标

将现存代码仓库转换成可审查、可追踪的统一图模型，并用批准的需求层与技术设计层驱动后续实现、测试和 MR Review。

## 用户

- 需求方：通过自然语言描述需求、回答业务问题、审查并批准统一图差异。
- 开发者：可以查看模型、实现证据和测试证据；不需要逐行审查 AI 生成的代码。

AI 模型、扫描器、验证器和 GitLab 是系统协作者，不是产品用户。

## 用户主线

1. 需求方接入一个或多个现存仓库。
2. 系统固定仓库 commit，在统一图的实现层建立可追溯的当前代码模型。
3. 实现层展示入口、方法调用、数据表读写和外部调用；测试层展示测试关联、观察和缺口。
4. 系统从实现证据聚合候选 `AS_IS` 需求主线，并把需求、设计、实现和测试节点关联在同一图中。
5. 需求方默认查看自然语言主线，点击节点或切换层级后在同一画布展开技术设计、代码和证据。
6. 需求方通过自然对话修正并批准项目基线。
7. 需求方描述新需求，系统在批准基线上实时生成需求层和技术设计层的 `TO_BE` 图差异与待确认问题。
8. 需求方解决问题并同时批准新的需求与设计 revision。
9. 实现 Agent 在独立 worktree 中按批准 revision 修改代码和测试。
10. 独立验证器执行变化场景、相关场景、完整回归和运行证据核对。
11. 验证通过后创建 MR，并展示 UML、代码和验证三类 Diff。

## 交互约束

- 唯一主界面默认由一张占满可用空间的交互图组成；自然语言对话默认折叠，可按需展开。
- 默认投影只表达用户目标和自然语言流程，避免大图一次铺开。
- 技术设计、代码实现和测试证据都是同一图的一等节点；用户通过层级开关或点击节点在原画布展开，节点详情显示完整属性和证据。
- 用户不需要直接编辑 UML 源文件、JSON 或测试配置。
- 所有模型元素使用稳定 ID；布局变化不得产生语义 Diff。

## 模型约束

- 所有层级共享的节点、关系、revision、交互投影和批准规则以 [统一交互图模型](graph-model.md) 为准。
- 需求层的语义和完整性规则以 [需求行为图定义](requirement-graph.md) 为准。
- 代码扫描形成的实现层与测试证据规则以 [技术实现图定义](implementation-graph.md) 为准。

- `AS_IS`：当前代码实际实现或可静态推导的行为。
- `TO_BE`：需求方批准的目标行为。
- `OBSERVED`：测试运行实际产生的行为和副作用。
- `INFERRED`：AI 暂时推断、尚未确认的内容。
- `INFERRED` 不得静默升级为需求事实。
- 存在未解决问题时不得批准 revision。
- 没有同时批准需求层和技术设计层的图 revision 时不得启动实现。

## 第一里程碑：对话生成需求图并在批准后开发

`sdbp-review` 先用本次 Codex 对话完成自举开发；自举完成后，应用自身提供同样的流程：

1. 用户在自然语言对话中描述一个新需求。
2. AI 分析需求，并检查完成需求建模和开发所必需的外部依赖与人工决策。
3. 缺少必要信息、凭证来源或技术决策时，AI 必须继续询问，不得自行猜测。
4. 信息完整后，AI 生成统一图差异：默认投影保持简洁，但技术设计作为可展开节点实时出现在同一画布。
5. 用户可以继续对话要求修改需求或技术设计；每次修改都形成新的候选语义 Diff。
6. 用户通过明确的“批准并开始开发”操作同时确认需求层和技术设计层，不能从含糊的自然语言推断批准。
7. 系统冻结不可变需求 revision，随后才允许实现 Agent 创建隔离 worktree 并开始开发。
8. 实现中发现新的必要决策或需求冲突时，必须停止开发、返回对话并等待新的批准。

第一版必须留下可以观察的开发运行状态和结果；自动测试、完整代码模型与 GitLab MR 在后续里程碑补齐。

第一里程碑的成功标准：没有明确批准时绝不写代码；批准后实现 Agent 收到的输入与用户看到并批准的需求、技术设计及内容哈希完全一致。

### 已确认的 AI 入口

- `DEC-AI-001`：第一版直接调用当前用户已经安装并登录的本机 `codex` CLI，不接入 `sdbp-agent`、OpenAI API 或 Anthropic API。
- 建模调用使用 `codex exec --ephemeral --ignore-user-config --sandbox read-only --json`；需求、完整对话上下文、当前候选模型和固定输出 Schema 通过标准输入传入。
- 实现调用只在批准后创建的隔离 Git worktree 中使用 `codex exec --ephemeral --ignore-user-config --sandbox workspace-write --json`。
- 应用使用参数数组直接创建子进程，不经过 shell，不允许用户修改可执行文件或追加任意命令参数。
- `codex` 不存在、未登录、退出非零、超时或输出不符合 Schema 时，运行进入可见失败状态；不得猜测结果、批准模型或进入下一阶段。
- 第一版应用直接运行在宿主机，复用当前用户的 Codex 登录状态；不向 Docker 复制或挂载 Codex 凭证。
- 后续切换 OpenAI 或 Anthropic 协议属于新的已批准需求；第一版不为它预建 provider 接口、工厂或兼容配置。

## 后续里程碑：当前代码建模与展示
